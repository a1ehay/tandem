# Application and service rules

- Один сервис/use case должен выражать конкретный бизнес-сценарий и иметь одну понятную ответственность.
- Размещать здесь бизнес-правила, авторизацию на уровне ресурсов, допустимые переходы статусов, координацию репозиториев и транзакционные границы.
- Не импортировать Spring MVC, Servlet API, HTTP DTO, JPA entities или JDBC-типы в application/domain contracts.
- Для зависимостей от хранилища объявлять узкие порты по нужным use case; реализации находятся во внешнем `repo`-слое. Высокоуровневый сценарий зависит от контракта, не от конкретного адаптера.
- Транзакции задавать на публичных application/service операциях. Не включать внутрь транзакции медленные внешние вызовы; внешние эффекты выполнять после commit или через надёжный отдельный механизм, если появится такая потребность.
- Не добавлять интерфейс для каждого класса автоматически. Абстракция оправдана границей, несколькими реализациями или необходимостью изолировать внешний ресурс.
- Обеспечивать атомарность связанных изменений и явно обрабатывать конфликтующие переходы состояний.
