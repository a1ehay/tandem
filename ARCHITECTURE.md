# Планируемая архитектура Tandem

Этот документ описывает целевые границы сервисов. Они являются планом: Go-сервис пока не реализует сетевые протоколы, API, авторизацию или бизнес-логику.

## Java Core Service

Существующее приложение в `backend/` остаётся Java 25 / Spring Boot сервисом. В целевой архитектуре Core отвечает за:

- пользователей и авторизацию;
- преподавателей и учеников;
- расписание и уроки;
- домашние задания;
- основную бизнес-логику и постоянные бизнес-данные.

PostgreSQL и миграции Flyway остаются в существующих `compose.yaml` и `database/`. Миграциями бизнес-схемы владеет Java Core.

## Go Realtime Service

`services/realtime-service/` подготовлен для отдельного Go-сервиса. В будущем его зона ответственности может включать:

- WebSocket соединения и управление их жизненным циклом;
- онлайн-доску и распространение её событий;
- присутствие участников в занятии (presence);
- доставку realtime-событий между подключёнными участниками.

Сервис не должен становиться владельцем бизнес-сущностей Core. Если позднее realtime потребуется собственное постоянное хранилище, его схема и миграции должны быть отделены от схемы Core.

## LiveKit

LiveKit остаётся отдельным медиатранспортом для аудио- и видеосвязи. Go Realtime Service не дублирует передачу медиа.

## Планируемое взаимодействие

Предполагается, что frontend будет обращаться к Java Core по HTTP для бизнес-операций и подключаться к Go Realtime Service для realtime-взаимодействия. При необходимости Go будет запрашивать у Core решение о доступе к занятию. Конкретные API-контракты, аутентификация межсервисных запросов и формат событий предстоит определить и реализовать отдельно.

На текущем этапе сервисы не интегрированы, а в репозитории не добавляются endpoints, WebSocket, авторизация или бизнес-логика.

## Существующие пути и инфраструктура

Java приложение остаётся в `backend/`: перенос в `services/core-service/` затронул бы пути, сборку и инструкции уже независимого Maven-проекта. Frontend, Cloudflare Worker, Flyway runner и корневые Compose-конфигурации также остаются на текущих местах.

Каталоги `infra/compose/`, `infra/docker/`, `infra/env/` и `infra/redis/` зарезервированы для будущего развития инфраструктуры. Они не содержат копий текущих конфигураций и не подключают дополнительные сервисы.
